# Process

## 1. Request intake

- `PM` or `Senior Product` reads user request.
- Identify the mission: what is the user asking for?
- Flag anything unclear as `ambiguous`.
- If unclear, do not start implementation.

## 2. Clarify mission

- Relevant members: `PM`, `Expert Ambiguity Analyst`, `Senior Agent Developer`, `Senior / Principal Dev Programmer`, `Expert UX/Product Designer`.
- Check assumptions and scope.
- If ambiguity exists:
  - `Q?` user with options or recommendations
  - `FYI: this is what we think user wants`
  - `doc: note + link` if needed
- Iterate until mission is clear.

## 3. Developer alignment

- Share the clarified mission with `DEV` team.
- Confirm there are no new technical ambiguities.
- If developers find new questions:
  - `DEV: Q? <short>` to `PM`
  - `PM` returns to user with recommendation
  - `PM: Q? user confirm <option>`
- Resolve until developers can start without blocking questions.

## 4. Plan and scope

- Define the work items and acceptance criteria.
- Assign `task:` to developers.
- Capture constraints and edge cases.
- Confirm `DONE` criteria before coding.

## 5. Build

- `DEV` executes tasks.
- Use `WIP` updates for progress.
- If blocked:
  - `DEV: BLOCK <reason>`
  - `DEV: Q? <short>` if clarification needed
- If requirement changes, repeat clarity loop.

## 6. Review and validate

- `REVIEW` inspects code / design.
- `QA` tests behavior and edge cases.
- If issues appear:
  - `REVIEW: PR#<id> changes needed`
  - `QA: TEST FAIL, bug <id>`
- Fix and validate again.

## 7. Delivery

- Confirm `QA: TEST PASS`
- Mark `DONE` when all acceptance criteria are met.
- `PM` or `OPS` completes release or handoff.
- Send final note: `FYI: delivered / done`

## 8. Feedback loop

- If user raises follow-up or bug:
  - repeat from step 2 with updated mission
- Keep cycles short and explicit.
